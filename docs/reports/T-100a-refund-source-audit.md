# T-100a refund-linking source audit

**Scope:** planning evidence from PaisaTrack `d654141`; synthetic/source inspection only. No owner rows, messages, or device data accessed. No Flutter tests run. This is a proposal for owner review, not accepted accounting policy or shipped behavior.

Related: [delivery plan](../plans/three-feature-delivery.md) and
[T-100 accounting brief](../tasks/T-100.md). This source-only preparation does
not close T-100a or authorize refund persistence/net totals.

## Findings

- **The refund correlator is not wired into ingestion.** GitNexus `context correlateRefund` resolves exact incoming references only from `test/capture/refund_linking_test.dart` (three calls); `rg` confirms the only production definition is `lib/capture/event_correlator.dart:237-307`. It returns a candidate `EventCorrelationResult`, not a persisted link. The exact-reference branch takes the first matching candidate without proving uniqueness (`:243-261`); the fallback matches equal/prefix merchant strings and a refund amount no greater than the purchase (`:264-304`). Neither path checks that the input row is actually a credit, nor candidate settled/deleted/duplicate/analytics/source-policy state, prior linked refunds, cumulative cap, or uniqueness against existing edges. Its ±30-day window is a heuristic, not approved policy. `refundAutoLinkThreshold` is currently only defined/defaulted (`lib/data/repositories/feature_flag_repository.dart:133-138,264-266`, `lib/core/constants.dart:86`); text search found no production consumer.
- **Persisted links are generic storage, not refund accounting.** `TransactionLinks` has endpoints, type, confidence, basis, creator and timestamp, with only an ID primary key and no direction/type/amount/pair uniqueness rule (`lib/data/db/tables/transaction_links_table.dart:5-19`). The only production writers found are the duplicate `echo` insert in `lib/capture/sms_ingestion.dart:484-496` and system-generated `transfer_leg` reconciliation in `lib/data/repositories/payment_source_repository.dart:222-289`. Existing refund-link fixtures show the convention `fromTxnId=credit/refund, toTxnId=debit/original`, but no production contract enforces it.
- **Financial events are currently dormant.** `FinancialEvents` has unique `eventKey`, `kind`, `netAmountPaise`, `currency` defaulting to INR, and times/state/confidence (`lib/data/db/tables/financial_events_table.dart:3-18`). Production text search found no read or write; the only direct inserts are migration/backup tests. It is created alongside transaction links in migration v10 (`lib/data/db/database.dart:193-195`; current schema v19 at `:58`). It is not in encrypted archive table lists/payloads; restore explicitly clears it (`lib/features/backup/encrypted_backup_service.dart:875-888,1110-1123,1930-1943,1950-1968`). A test inserts an event, imports an archive, and expects the event table empty (`test/features/backup/encrypted_backup_service_test.dart:452-526`). Do not reuse this table as the refund ledger without deciding backup/version compatibility and whether its single-currency net field can represent the contract.
- **Current eligible spend is gross debit, and refund edges are ignored.** `FinancialEligibility.base` includes only settled, non-deleted, non-false-positive, non-duplicate, non-analytics-excluded, non-owned-transfer rows (`lib/data/analytics/financial_eligibility.dart:13-24,43-55`); `spendingDebit` adds debit and spending-category criteria. No refund joins occur. Dashboard totals group eligible rows into debit and credit separately; INR headline totals use the same base, and category/payee/trend totals use eligible debit only (`lib/data/repositories/dashboard_repository.dart:144-178,208-227,245-259,282-300,367-380`). Dashboard budget/safe-today/runway use `debitTotal` (`lib/features/dashboard/dashboard_providers.dart:341-375`). Ask’s `net` currently means eligible settled credits minus eligible spend debits, not purchase spend after linked refunds (`lib/intelligence/assistant/query_engine.dart:215-225`). Burn rate, anomaly detection, and insight evidence also select eligible debits (`lib/intelligence/burn_rate_forecaster.dart:55-78`, `lib/intelligence/anomaly_detector.dart:34-43`, `lib/intelligence/insights_engine.dart:99-121`); claim evidence filters the same debit contract (`lib/intelligence/claim.dart:397-416`). Thus refunds need one shared, explicitly named net-spend projection and consistent callers; a generic cash-flow net must remain distinct. Recurring detection groups settled credits and debits as separate recurrence streams, not a spend total (`lib/intelligence/recurring_detector.dart:60-94`).
- **Currency evidence must stay bucketed.** `SourceCurrency.sameBucket` matches identical explicit codes; if codes are absent, symbols must match (including unknown↔unknown), and a bare-symbol bucket never matches an explicit ISO code (`lib/data/models/source_currency.dart:3-24`). ADR 0017 forbids implicit FX. Dashboard exposes source-currency totals separately; its headline budget and current INR aggregate are INR-only. No cross-currency subtraction should be introduced.
- **Backup, reset, and migration.** `transaction_links` is archived/restored and optional in old archives (`encrypted_backup_service.dart:42-47,875-888,1116-1119,1266-1269,1930-1943`); recovery tests verify a synthetic refund link survives generation restore (`test/features/recovery/database_recovery_service_test.dart:239-309`). Restore clears links before transactions (`:1950-1968`). Full app reset deletes DB generations and recovery archives (`lib/features/settings/app_data_reset_service.dart:35-119`). v10 migration tests cover table creation, generic `reverses` insert, and unique financial-event key, not refund rules (`test/data/db/app_database_v10_migration_test.dart:16-106`).
- **Existing test evidence is narrower than its names can imply.** `test/capture/refund_linking_test.dart` has only three pure correlator-result tests: exact ref, single-candidate partial amount/name, and ambiguous fallback. It does not insert edges or calculate net. `test/data/financial_eligibility_parity_test.dart` checks SQL/Drift/row-helper agreement for eligibility but does not apply links. `test/intelligence/net_spending_contract_test.dart` proves current gross debit/credit semantics for dashboard, burn rate, and Ask. Backup/recovery tests prove generic link persistence/restore; they seed synthetic links directly. T-100 currently names `test/capture/event_correlator_test.dart` in a characterization command; the source test present for refund correlation is `refund_linking_test.dart`.
- **PV-04 remains an explanation dependency.** T-172 names deleted, duplicate, transfer, pending, reversed, refund, and excluded-source explanations as a shared integrity contract. T-100b2/c must expose which original and refund evidence changed gross-to-net and how an unlinked/ambiguous credit was treated; a net number without linked/unlinked explanation is insufficient.

GitNexus exact contexts support `correlateRefund` (test-only incoming calls), `FinancialEligibility` (dashboard, assistant, burn, anomaly, insights, claim and other consumers), `DashboardRepository._loadTotals`, and `AssistantQueryEngine._transactions`. Index refreshed to HEAD before these queries. Its flow inventory is not exhaustive: it reports 407 flows while 1,059/1,259 candidate entrypoints are unranked, 1,422 callees skipped at maxBranching, and 34 walks cut by trace budget. An absent graph edge/flow is not treated as proof of no caller; relevant write and read claims above were corroborated with text search.

## Proposed contract for owner decision (not approved)

1. Preserve the original debit and posted credit as immutable source transactions. A refund relationship is oriented `from=refund credit` → `to=original debit`; the edge classifies the credit, it does not create a second transaction. `reverses` is separate from `refunds`; `repays` is for reimbursement/repayment and does not silently mean merchant refund.
2. Only a settled, positive, credit refund row and a settled, positive, eligible spending debit can participate. Reject deleted, not-a-transaction, duplicate-suppressed, pending/failed/reversed, analytics-excluded, or owned-transfer rows; do not alter these eligibility flags as a side effect. Require the same complete `SourceCurrency` bucket; never convert. A link to an excluded purchase should not secretly change headline spend—either reject it or expose a separate adjustment reason, owner to decide.
3. **Candidate policy proposal:** exact reference is evidence for a proposal, not automatic persistence, unless there is exactly one compatible candidate and owner approves the exact-reference auto-link rule. Multiple exact-ref candidates remain unresolved. Merchant/amount/window matches are review suggestions only. Do not treat the existing 30-day heuristic or 0.90 flag as approved. Recheck current persisted rows and links atomically at confirmation; repeated ingestion must not duplicate an edge.
4. V1 supports many distinct refund-credit rows against one original purchase, with the sum of approved linked refund amounts capped at the original amount. An attempt to exceed the remaining amount is rejected whole and left visibly unlinked for review (no silent cap). A refund credit can target one original only in this v1 proposal. If one posted credit must be allocated across multiple purchases, current `transaction_links` lacks per-edge amount; add an explicit allocation amount/schema or leave it unresolved rather than splitting by guess.
5. Show separate **gross spend**, **linked refunds/reversals**, and **net spend**; keep ordinary credits, repayments/reimbursements, cashback/rewards, and unlinked credits separate. Unlinked credits never reduce purchase spend just because amount/name/date looks similar. Ask's cash-flow `net` should remain separately named/calculated if the refund-adjusted spend metric is added.
6. Reversals proposed to offset their original in the original purchase period. Refund period is unresolved: choose purchase-period restatement, posting-period adjustment, or both selectable views. Preserve the posted date/evidence in either case. For each currency bucket, `net spend = eligible gross debit − owner-approved linked refund/reversal allocations` subject to the selected period rule; never combine buckets.
7. Make link add/remove reviewable and idempotent with durable, stale-safe Undo. Undo removes only the relationship/projection created by that decision, preserving both transactions and newer edits. No deletion of credit rows as a dedupe shortcut.
8. Prefer reusing `transaction_links` for single-original whole-credit allocations if it can enforce direction, uniqueness and cap transactionally. Do not reuse dormant `financial_events` without a specific event model plus encrypted archive/restore tests; it is currently unarchived and has only one currency field. No schema migration is justified by this audit alone. Any allocation amount, reviewer/undo receipt, or period policy persisted in schema needs ADR + additive migration + both backup encodings + recovery/reset/FK coverage.

## Owner decisions required before T-100b1/b2/c

1. Period attribution: should late refunds restate the purchase period, reduce spend only when posted, or support both views? Does a reversal always restate original period?
2. Credit taxonomy: when does an inbound credit count as a merchant refund versus reimbursement (`repays`), cashback, reward/statement credit, chargeback, returned payment, or ordinary income? Which classes reduce net spend, and which only cash-flow/liability?
3. Partial allocation limits: may one refund credit apply to several purchases (requires per-link amount), may one purchase receive many credits, and should over-refund reject the entire new allocation or allow only its valid remainder? What happens to excess?
4. Automation boundary: may a unique exact reference auto-persist a link, or must the user confirm every candidate? Is merchant/name/amount matching review-only? Should the existing 30-day window remain, change, or be ignored when exact reference is present?
5. Scope/presentation: should linked refund credits for analytics-excluded/owned-transfer/non-spending purchases ever alter any spend view? Must both gross and net appear together in Dashboard/Trends/Ask, and which source-period/date is the default?
6. Reimbursement meaning: should shared-cost repayments or insurance reimbursements reduce category spend, be reported as income, or remain separate adjustments? Are they allowed to reference more than one expense?

**Readiness gaps:** T-100a has no accepted owner answers yet; current link schema does not encode allocation amounts or unique relationship semantics; financial events are neither consumed nor archived; aggregate callers disagree by metric (gross spend vs cash-flow net) and need one approved output contract. The audit establishes these facts but does not claim T-100 or its implementation gates are complete.
