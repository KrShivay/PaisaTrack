## Synthetic audit matrix proposal

This is audit classification only: expected result is “candidate / ambiguous / not card evidence,” with zero writes. It is not approval for production matching.

| Synthetic source/event | Evidence available | T-190a1 report result | Must not do |
|---|---|---|---|
| HDFC `card`, `xx1234`, card-purchase template | `channel=card`, issuer text, masked suffix | Card-channel candidate; credit/debit product and ownership unconfirmed | Mark owned or credit card solely from channel |
| Axis `card`, `xx1234`, same suffix | Same inferred key inputs, different issuer label | Conflict only if retained hint/channel evidence maps to multiple source IDs or recorded labels; an already-merged collision is unobservable | Split or rewrite existing source/transaction IDs |
| HDFC `netbanking`, `xx1234` | Same hint but different channel | Separate inferred source today; relation to card remains unproven | Pair it to a card by suffix alone |
| `wallet`, `xx1234` or wallet top-up | Wallet/card wording may identify channel only | Wallet candidate; funding method/product remains unknown | Count top-up as both card purchase and wallet purchase |
| Bank debit + card bill-confirmation credit, same amount/currency/time | Two source rows, potentially generic `ownedTransferId` / `transfer_leg` | Candidate repayment pair only if exact stored generated edge is present; ownership confirmation absent | Create a liability allocation or treat confirmation/debit as independent expense/payment |
| Card purchase followed by matching opposite credit | Could be refund, reversal, cashback, reward, or echo; helper may propose links from amount/ref/merchant | Unresolved unless a persisted, reviewed link and its evidence are present | Net as refund or alter original amount |
| Pending authorization, settlement, decline, statement/due notice | Message classifier/parser/template/lifecycle evidence varies | Pending/failed/nontransaction or template-backed candidate, retain evidence/confidence | Treat a hold or due snapshot as a settled purchase/liability delta |
| Same masked suffix at same channel, institutions absent | Current source has no institution in key | Identity uncertainty; no conflict proven by one source alone | Infer institution or create duplicate ownership silently |

## Bounded first UI slice proposal

Keep T-190a1 read-only. Add a separate “Card source audit” route directly from Settings, bypassing the existing Accounts provider because it reconciles transfers on load. The report groups synthetic/audited rows by *current stored source id* and displays: stored kind/channel, masked hint, institution/nickname when present, number of associated transactions, and explicit provenance text (“inferred from account hint + channel; ownership/product not confirmed”). Add a separate “possible card transaction” section using existing stored `channel=card` and parser/evidence metadata as candidates, with lifecycle/status and currency visible; include rows with unknown/incomplete evidence as “needs review” rather than omitting them. Flag repeated inferred identity inputs across institution labels as a collision, but do not split or relink rows. The report must not call `updateSource`, reconcile transfers, set flags, create links, or change totals. Verify source rows, transactions, links and aggregate snapshots byte/value-identical before and after report construction. If no real institution provenance exists, state “institution unavailable”; do not guess from sender/channel.

A read-only audit report is safer than adding another ownership switch: the existing settings screen already has direct `Owned by me`/analytics/activity mutations, while T-190a1 expressly forbids ownership writes. Ownership/instrument confirmation with full preview and durable undo belongs in separate T-190a2, after its product contract and review.

## Owner decisions and unresolved questions

T-190a1 itself can report uncertainty without resolving these; obtain answers before T-190a2 or accounting implementation:

1. What product types may be shown as cards: credit only, or debit/prepaid/add-on cards too? Is “card” channel ever enough for a candidate label, and which explicit issuer/document evidence raises confidence?
2. Must ownership confirmation be explicit per source before any source affects generic transfer exclusion? Current default is owned=true and current settings toggle has immediate aggregate effect. Should legacy inferred rows be grandfathered, warned, or queued for confirmation in a separately approved slice?
3. How should same last-four/channel across institutions, replacement cards, supplementary cards, and one shared issuer bill be represented? Separate source identity versus owner-confirmed liability group?
4. Which candidate event classes are in the first user-facing review: purchases only, or also repayments, auth/settlement, reversals/refunds, fees/rewards and statement notices? Which evidence should be shown so the user can reject a false match?
5. T-190a2 previews reconciliation before ownership/instrument writes; what must its preview include (exact rows, per-currency totals, existing user links, analytics effects) and what durable undo/retention window is acceptable?
6. For later accounting, decide refund-period default, fee category/period, cash-advance categorized-spend policy, rewards vs cashback, credit-balance display after overpayment, statement-cycle view, add-on-card grouping, and combined EMI treatment. These remain proposals in ADR 0020/plan, not defaults to silently ship.
7. Confirm whether T-100's separate refund contract remains the owner of refund linking and net-spend policy; T-190d should depend on that decision rather than implementing a second refund system.

## Source-backed boundary

- T-190 accounting is `PLANNED`; ADR 0020 is `Proposed`. ADR 0027 accepts only the isolated read-only host audit. No schema, ownership confirmation or accounting implementation is approved.
- Current code can identify some card-*worded* transactions and generic inferred sources, but it cannot prove a credit-card product or user ownership. Existing payment-source settings can mutate ownership immediately, so the audit path must be read-only and must not present inferred flags as confirmed facts.
- Current generic spend and source-transfer projections are not a card ledger. Existing correlation helpers, schema types and fixture names are capability ingredients, not proof of persisted card relationships/accounting.
