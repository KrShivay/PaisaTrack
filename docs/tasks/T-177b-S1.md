# T-177b-S1 — Gated exact-payee category suggestion

Status: Host implementation complete and independently reviewed on
`codex/merchant-suggestions`. This closes only the bounded T-177b detail-screen
slice; T-177a/T-177f production gates and owner/device acceptance remain open.
Contract: [ADR 0025](../decisions/0025-category-memory-suggestions.md),
[smart transaction assistance plan](../plans/smart-transaction-assistance.md),
and [T-177](T-177.md).

## Goal

On transaction detail, offer an existing category when at least two distinct,
eligible, explicitly confirmed transactions for the same exact payee have the
same latest category outcome. Explain that the proposal comes from the user's
prior category choices. A tap changes this transaction's category and writes
one explicit feedback outcome. An exact before/after receipt guards Undo.

## Scope and boundaries

- Use exact persisted VPA identity, including PSP handle, corroborated against
  the transaction row's full raw VPA. With no VPA, use the persisted normalized
  merchant-name key, corroborate the transaction's current raw name, and abstain
  when matching history contains multiple distinct VPAs. No embedding,
  similarity, fuzzy matching, or silent identity merge.
- Reuse the source-category-provenance check used by
  `AdaptiveThresholdPolicy`; accepted history must be distinct, current,
  explicitly corrected or status-confirmed under recognized user contexts.
  Ignore manual, deleted, nontransaction, duplicate, unsettled, analytics
  excluded, unprovenanced, undone, and status-only parse-confirm rows.
- Require all eligible latest outcomes to agree on the same active category.
  Conflicts, ambiguity, missing evidence, and deleted categories abstain.
- Keep category choice separate from transaction eligibility, currency, and
  account ownership. Do not change a person's VPA or financial exclusion.
- Keep the detail read provider gated off by default. Tests may inject the gate
  to exercise the visible panel. T-177a's consented chronological holdout,
  owner-selected thresholds/cohort, and live/history/resume device evidence
  remain open. Any production suggestion stage also waits for the T-177f staged
  release decision. No automatic categorization is in scope.
- Acceptance rechecks the suggestion, matching rule, and current transaction
  inside a database transaction. It writes category plus one feedback row only;
  Undo succeeds only while the complete saved after-row and feedback receipt
  still match. It never calls `correctCategory`, which would also confirm
  status and may create a future rule.
- T-200 confirmation records status and parse feedback only. Do not make it a
  category outcome or change its amount/status/parse behavior.

## Acceptance evidence

- Pure outcome tests preserve `AdaptiveThresholdPolicy` behavior while proving
  only explicit category correction or explicit Activity/Sort confirmation
  yields a trusted current category. T-200 parse confirmation, automatic,
  unconfirmed, status-only, manual, undo, and missing-provenance rows do not
  qualify.
- Repository tests prove two distinct unanimous outcomes suggest the active
  category; one outcome, mixed outcomes, changed latest category, deleted
  category, same-name/different-VPA, ambiguous name-only history, and every
  excluded source row abstain. The target transaction is not counted as its own
  history.
- Provider/widget tests prove default-off has no suggestion; injected enablement
  renders category plus plain provenance/count explanation. Accept changes only
  category, creates the expected explicit feedback, preserves transaction
  status/amount/direction/parse provenance, and Undo restores the prior
  category. Explicit matching rule, current user correction, or current
  category already equal to the candidate suppresses the panel.
- Detail-flow checks preserve an unsaved note draft through successful Undo and
  stale-accept refresh, while restoring the category chip and accessible row
  label from persisted state.
- No capture, history-import, or resume path is modified. Synthetic database
  rows only; no owner data, phone, APK, network inference, or release enablement.
