# T-165b — Indexed owned-transfer matching and stale-edge cleanup

**Status:** Complete. This implementation owns the existing owned-transfer
reconciliation path and closes the T-190b1 prerequisite; it does not implement
card-payment allocation.

## Goal

Match only uniquely supported, settled debit/credit pairs between distinct
active owned payment sources. Keep transaction flags and generated relationship
edges in sync when transactions or source ownership/activity change.

## Acceptance criteria

- Candidate matching runs in SQL with bounded `ts` range probes that can use
  `idx_transactions_ts`; it does not materialize every edge in a dense
  same-amount cohort. Preserve the inclusive ±600,000 ms window.
- A pair is accepted only when the debit has exactly one eligible credit
  candidate and that credit has exactly one eligible debit candidate. Check
  uniqueness across the full candidate set (including different owned sources)
  and leave all ambiguous rows unlinked.
- Require opposite debit/credit directions, equal amount, distinct active owned
  sources, settled lifecycle, no deletion, duplicate, or “not a transaction”
  mark, and the same complete currency bucket (`currency_code` and
  `currency_symbol`, with null-safe equality for legacy unknown values).
- Reconcile transaction flags and generated edges in one database transaction.
  Change only flags that differ; a second unchanged run writes no rows and keeps
  existing generated edge IDs, endpoint orientation, confidence, and timestamps.
  New `ownedTransferId` values use length-prefixed endpoint IDs; the prior
  underscore-concatenated value can collide for IDs containing underscores and
  is normalized on the next reconciliation.
- Delete only stale edges whose provenance is exactly
  `created_by = 'system'`, `basis = 'indexed_owned_transfer'`, and
  `link_type = 'transfer_leg'`. Preserve user-authored and other generated
  links, including an ID collision; never overwrite a user link to create a
  generated one. Use deterministic debit-to-credit endpoint orientation and
  deterministic IDs for generated edges.
- Reconciliation after amount/date/currency/direction/eligibility/payment-source
  edits, “not a transaction” marking, ownership changes, and active-state
  changes removes stale generated edges and clears only the affected transfer
  flags. Analytics continue excluding each paired transfer once and do not
  double-count either side.
- No schema migration unless measured before/after `EXPLAIN QUERY PLAN` proves
  existing indexes cannot support the bounded candidate query; any required
  index needs ADR 0022 and an additive migration with migration tests first.
- Add synthetic adversarial tests for same amount/date across several owned
  sources, two debits competing for one credit, exact window boundaries,
  stale pairs after row/source changes, user-link preservation and collisions,
  true idempotence, rollback on write failure where practical, and analytics.
- Add a large-history performance check with a dense ambiguous cohort. Record
  row counts, elapsed time, SQLite version, and query plan in this brief; keep
  timing evidence informational or use a generous threshold to avoid a flaky
  wall-clock gate.

## Baseline measurement (before implementation)

Current behavior is a SQL self-join, not a Dart nested loop. It matches all
equal-amount, opposite-direction rows and applies
`ABS(t1.ts - t2.ts) <= 600000`, then greedily accepts the first unused pair.
This can generate a quadratic candidate result for a dense same-amount/time
cohort and can guess in ambiguous graphs. Before building the replacement, run
`EXPLAIN QUERY PLAN` for the current query against the existing transaction
indexes. Record SQLite version, planner output, and a synthetic baseline with a
dense ambiguous cohort alongside final evidence below.

The baseline and replacement SQL were measured with Python sqlite3 3.53.3 in
an in-memory, schema-equivalent database carrying the repository's existing
transaction/source indexes. The old plan searched
`idx_transactions_not_transaction` on both self-join sides and used a temporary
B-tree for ordering; the timestamp index could not narrow the join because of
the `ABS(ts1 - ts2)` predicate. On 10,160 synthetic rows, including an 80-by-80
dense ambiguous cohort, the old query emitted 12,800 directed candidate rows
and took 17,044.6 ms including `fetchall()`. The old Dart greedy pass then
selected one of those ambiguous pairs. The replacement query returned zero
accepted pairs in 25.0 ms; both capped inner probes searched
`idx_transactions_ts (ts>? AND ts<?)`. Only the final pair output used a
temporary B-tree; neither candidate probe sorted its timestamp window.

Each eligible transaction performs two timestamp-index range probes capped at
two rows. Dense matching cohorts therefore do not materialize all candidate
edges; adversarial windows with many nonmatching rows can still require scans
within each ±10-minute range, so total work depends on local window density.
The SQL timings are a same-fixture host comparison, not an Android-device
latency claim or a universal complexity bound. The Flutter test records full
repository reconciliation time; its timing is informational rather than a
machine-dependent pass threshold.
