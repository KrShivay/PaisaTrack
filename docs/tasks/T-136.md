# T-136 — Counterparty identity

`MerchantResolver.normalizeAlias` is `uppercase → strip non-alphanumeric`, so
`paytm-9876543210@ptys` is unique per payer. Every person you pay mints a
merchant row and a review item. Device testing recorded 6,807 review rows across
2,467 merchants on one install.

### T-136a — Counterparties table and identity parser   [P1] [~L]
Files:    `lib/data/db/tables/counterparties_table.dart` (new),
          `lib/enrichment/counterparty_key.dart` (new)
Depends:  T-134a
Change:   Table (id, kind, identity_key unique, display_name, inferred_name,
          psp_family, merchant_id nullable, first_seen, last_seen, txn_count).
          Parser turns raw text into a structured key:
          - VPA → split local part and PSP. Strip a trailing digit run ≥6 **only
            when the remaining core is a known PSP token** — getting this
            backwards is how `PAYTM` swallows every Paytm user.
          - Known aggregator QR prefixes (`paytmqr`, `bharatpe`, `q`, `merchant`,
            `mab`) → merchant with an opaque core.
          - Card descriptors → strip trailing geography and store numbers
            (`SWIGGY INSTAMART BANGALORE`, `RELIANCE SMART 4471`).
          Phone numbers are hashed into the key, never stored raw.
Tests:    Table-driven cases per rule, including the PSP-token guard. No raw
          phone number appears in any stored key.
AC:       Two payments to the same person via different PSPs share one key.
Note:     `~L`. Split as (i) table + migration, (ii) VPA parser, (iii) card
          descriptor parser.

### T-136b — Person/merchant split in the ladder   [P1] [~M]
Files:    `lib/enrichment/merchant_resolver.dart`, `lib/enrichment/categorizer.dart`
Depends:  T-136a
Change:   Classify `kind` as person | merchant | institution | self | unknown.
          Only `kind='merchant'` promotes into `merchants` and enters the
          embedding search. **People never reach the categorization ladder** —
          they default to a P2P/transfer treatment instead of bottoming out at
          `other` at confidence 0.3, which is the value that guarantees a review
          row.
Tests:    A P2P payment creates no merchant row and no review item. A merchant
          payment behaves exactly as today.
AC:       Review inflow per 100 transactions drops below 5 against the T-143
          baseline.

### T-136c — Previewed, reversible backfill   [P1] [~M]
Files:    `lib/features/settings/payee_labels_screen.dart`, backfill service
Depends:  T-136b
Change:   Apply structured keys to **new** transactions first, then offer a
          backfill using the existing preview-and-reverse label-merge machinery.
          Never a silent history rewrite. `merchant_raw` is never overwritten.
Tests:    Preview lists affected rows before any write; undo restores prior
          state; raw source fields are untouched.
AC:       Merchants per 1,000 transactions falls ≥70% against the T-143 baseline.
Rationale: `docs/sms-intelligence-design.md` §8.1.
