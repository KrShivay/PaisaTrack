### T-177a progress — threshold evidence safeguard

The existing threshold recomputation treated every `status='auto'` row as a
correct outcome. This is invalid because silence is not a user-confirmed label.
The safeguard now considers category corrections and explicit confirmation
feedback linked to category prediction provenance. Status-only confirmations,
manual entries, and unreviewed automatic rows do not lower the threshold. The
adaptive metadata key is versioned so values trained by the old silence rule
are discarded and the static threshold is used until enough eligible evidence
is collected. Deterministic fingerprints cover completed chronological
50-outcome cohorts; feedback revisions replay all completed cohorts from the
static default. If undo or a category change leaves fewer than 50 eligible
outcomes (or removes the category entirely), the learned value, count, and
fingerprint are cleared and the static threshold is used. The stored cohort
fingerprint is a streaming SHA-256 digest rather than a copy of the event list.

This is only a verified safety milestone, not completion of T-177a. The
transaction detail now has a separate evidence-backed parse-confirm action;
that event records parser feedback only and does not confirm the transaction,
change its category, or count as category-threshold evidence. v1 and v2
threshold/count metadata are ignored by the v3 evidence-fingerprint state.
The live/history/resume source matrix and T-140/T-143 component status are now
documented in the T-177a report. Real source-evidence coverage, consented
holdout cohort sizes, precision, and accuracy/coverage baselines remain open.
The parse-confirm event uses a versioned marker; the public-template
ledger ignores legacy unvalidated positive rows, filters invalid/deleted/
duplicate evidence, rebuilds stale v1 cache on first read, and keeps confirmed
evidence after raw SMS retention expires. This provenance milestone does not
complete T-177a.

`CounterpartyKeyParser.identityKey` changed format in R2. VPA identities now
retain the PSP as part of the key (for example, `ravi@ybl` and `ravi@okaxis`
remain separate). Merchant names remove only known capture wrappers and legal

transaction rows by production code.

Stored `merchant_aliases.alias`, rules, and payee evidence keep the pre-R2
normalization until a schema migration is approved. Resolver lookup tries both
name keys, while R2 writes only aliases using the stored-key contract. A later
v20 migration must re-key aliases with explicit collision handling for
`merchant_aliases.alias`, then move rule match values and payee evidence in the
same migration/backfill operation so correction and capture lookup contracts
cannot diverge. Preserve
user aliases on collision and report ambiguous merges for review; never choose
a merchant silently. Migration tests must cover rollback and coordinated rule
and evidence movement. No v20 migration or re-key is part of R2.

### R3 rules and Ask on resolved identity

Rule precedence is exact counterparty VPA, resolved `merchant_id`, exact
normalized merchant key, then R1 `merchant_legacy` word-boundary matching.
The narrower VPA rule comes first so a per-VPA correction is never shadowed by
a merchant-wide correction. A merchant ID is eligible only when persisted
`confidence_json.merchant.src` records an exact link (`user`, `exact`, or
`new`); missing and suggestion/similarity sources use the R1 exact VPA/name
rule instead. Merchant ID sweeps include exact-source rows with that ID plus
rows with the current transaction's exact VPA or exact evidence name. This
keeps pre-R3 history reachable without widening a rule through old fuzzy
merchant links. Undo restores the prior rule state.

The R3 `merchant_id` match type is unknown to pre-R3 app versions, so rolling
the app back leaves these rules inert. A future v20 migration plan must account
for dangling `merchant_id` rules if merchant merges or deletes are introduced;
it must define reassignment or review behavior before those operations ship.

Ask resolves a merchant phrase across canonical names, user labels, aliases,
and captured evidence with whole-phrase boundaries. It filters eligible rows
using merchant ID, associated VPA keys, and normalized raw-name keys; when no
payee resolves it falls back to whole-token raw-name matching. Multiple payees
produce a clarification. Spending eligibility and per-currency totals remain
owned by the existing `FinancialEligibility` and `SourceCurrency` contracts.

R3 adds no schema migration. The R2 stored-key compatibility contract and
deferred coordinated v20 alias/rule/evidence re-key remain unchanged.

### Data flow and design constraints (for the ADR)

1. **Explicit input only.** User picks an image with the system photo picker
   (no `READ_MEDIA_IMAGES`/storage permission) or shares one to the app. No
   gallery scan, no background job, no new permission.
2. **Extraction is deterministic and advisory.** OCR text goes through regex
   field extractors (amount with `Rs`/`INR`/rupee sign, `dd Mon yyyy`/time,
   12-digit UPI reference, merchant/payee line, status word). The result is a
   `ReceiptEvidence` candidate set; per ADR 0011 a model may not create or
   amend amounts, and OCR text is untrusted data, never put into an LLM prompt
   as instruction. Length-cap and strip control characters before any display.
3. **A receipt is not proof of settlement.** "Payment successful" screenshots
   can be pending, reversed or edited. A receipt can only *attach evidence* to
   an existing settled transaction (from SMS) or propose an `expected_event`;
   it never creates a settled payment and never changes an amount.
4. **Matching** (pure Dart, T-177g3): candidates are transactions in the same
   currency with amount equal to the paise (no tolerance), date within
   +/- 1 day of the receipt date (+/- 3 days when only a date, no time),
   exact normalized UPI/reference match outranks everything, then merchant
   token overlap using the existing payee identity key. Output: ranked list
   with reasons; **ambiguous (>= 2 candidates within the top score band) or
   0 candidates => abstain** and let the user pick; never auto-commit.
5. **Retention.** Default: the image is processed in memory/app cache and
   deleted immediately after the preview closes; persist only the extracted
   fields the user confirms, plus a SHA-256 of the image bytes for duplicate
   detection (hash is irreversible, no pixels kept). Optional "keep image"
   is a separate opt-in decision; if allowed it lives in encrypted app storage,
   is covered by encrypted backup/restore and delete-everything, and has a
   per-item delete. Decision recorded in the ADR, not assumed here.
6. **Schema.** Prefer reusing `transaction_links` with a new
   `link_type`/basis over a new table; if a table is needed
   (`receipt_evidence`: id, txn_id, image_sha256, extracted_json, created_at)
   it is additive, and the integration child must ship migration test, backup,
   restore and delete-everything coverage. Not designed further until "go".
7. **Malicious/odd images.** Oversized images (cap decode to <= 4096 px long
   side and 20 MB), animated/multi-frame, prompt-injection text, RTL or
   mixed-script lines, screenshots of screenshots, near-duplicate images: all
   have defined behaviour (reject, truncate, or abstain) and tests in g3/g4.

### Go / no-go criteria (all must hold for "go")

| # | Criterion | Threshold | How measured |
|---|---|---|---|
| 1 | Offline & private | Zero outbound connections during recognition; no new permission; merged manifest diff shows no new `uses-permission`, service or provider beyond the SDK's own non-network components | Airplane-mode + blocked-network emulator run; `aapt dump badging` and merged-manifest diff before/after |
| 2 | Licence | Apache-2.0/MIT-class **or** an explicit owner waiver recorded in the ADR for a free proprietary SDK | ADR g1 |
| 3 | Size | Release ARM64 APK delta <= 8 MB (hard stop 12 MB); no change when the feature is unused (lazy init) | `apkanalyzer`/size diff against the candidate APK at the same commit |
| 4 | Accuracy on synthetic corpus (>= 120 rendered receipts across >= 6 layouts, light/dark, 2 font scales, English + Hinglish) | Amount exact >= 95%; date >= 90%; reference id >= 85% where present; merchant token recall >= 80% | Corpus runner (g2/g4/g5) |
| 5 | Matching safety | Top-1 correct >= 90% when a true match exists; wrong top-1 <= 1%; 100% abstain on 0-candidate and tied cases; 0 auto-commits | Matcher tests (g3) over the corpus plus a synthetic ledger |
| 6 | Performance | p95 recognition <= 2.5 s on a 4 GB-class device; extra peak RAM <= 150 MB; never run while the LLM runtime holds its RAM gate | Instrumented spike on emulator + target device |
| 7 | Reversibility | Feature removable without a data migration; deleting a receipt link leaves the transaction unchanged | Design review in ADR |

If criterion 1 or 2 fails the decision is **no-go** for that option regardless
of accuracy. If both options fail 4, the decision is no-go and the task is
closed with the report; Paddle is a separate, owner-approved spike.
