# T-167b — Accessible custom controls

Status: Host complete (independent review accepted 2026-10-04). This host-side slice covers the custom controls named
below; it does not close the separate T-167c/T-176 device and TalkBack gates.

## Acceptance

- Custom controls in Activity, Dashboard, Settings, and Weekly Review expose
  useful accessible names, appropriate control roles, and selected or enabled
  state when that state affects behavior.
- Every included tappable control has an actual hit surface and semantic bounds
  of at least 48×48dp. Small visual icons/text may remain compact inside that
  surface.
- Public-screen tests exercise control changes and callbacks, tap near exposed
  target edges, and inspect semantics at 320dp width with 2× text. No included
  control is scaled below its minimum target or clipped/overflowed.
- Disabled/loading actions expose disabled state and do not invoke callbacks.
- Preserve current navigation, filtering, category, theme, review, and notice
  behavior. Do not change financial logic, persistence, providers, or schema.

## Scoped inventory

- Dashboard: the four metric choices currently sit in a `FittedBox` and must
  remain legible/tappable without scaling; the “All” action announces its
  destination. The budget card and transaction rows expose button roles while
  retaining their meaningful child text. Period selectors, Material buttons,
  and any remaining custom actions are measured and semantically audited
  before exclusion. The existing greeting/streak/period controls already meet
  the screen's minimum target contract, covered by
  `dashboard_screen_test.dart`; this task leaves them unchanged.
- Activity: custom filter chips, search-clear, and dismissible transaction
  rows expose useful names, roles, and state. Keep payee, amount, date, and
  status descriptions available; preserve swipe, search, and filter behavior.
  Standard Material controls remain in place only after their semantic and
  target bounds are verified.
- Settings: theme choices expose their selected state; the reset-data card is
  announced as a button. Other custom primary actions are audited, while
  `ListTile`, switches, and standard Material actions remain in their existing
  form when their semantic and target bounds pass.
- Weekly Review: the card/list mode toggle announces its mode and selected
  state; Back, Change category, Skip, and Keep each have explicit names and
  truthful enabled state. The Sort card exposes its detail action as a named
  button. A list row has no default tap action or button role; it preserves its
  transaction description, exposes named Keep/Change category/Skip custom
  actions, and keeps its UPI QR action independently accessible. Existing
  callbacks and disabled Keep behavior remain unchanged.
- Shared `BloomNotice`: its optional action has a button role/name and reports
  disabled state when no callback is supplied, with a minimum target.

## Verification boundaries

Use regression-first widget tests through public screen entrypoints where the
state can be provided without changing production behavior. Keep screen-local
semantics in the relevant feature widget; introduce a shared helper only if the
same behavior is genuinely repeated. T-167d owns broad replacement of bespoke
gesture controls. T-167c/T-176 retain responsive-layout, bottom-inset, and
physical TalkBack/device acceptance. No physical-device or TalkBack check has
been run for this slice.

The initial compact Review card test reproduced a 201dp bottom overflow at
320×568dp and 2× text. The current T-167b changes make the card content
scrollable and adapt the list header/rows; the focused compact card and list
tests pass. This defect is no longer listed as a separate T-167c follow-up.
Dashboard category rows wrap long amounts instead of truncating them, and the
budget card stacks metadata and complete amounts at compact widths or 2× text.
The budget card also has a 402×874/2× presentation check. To preserve 24dp
clearance below the newly 48dp metric controls in short landscape, the
Dashboard reduces only the compact-landscape gaps; the full shell still
scrolls its lazy-built final Dashboard item into view before checking it clears
the floating navigation. Sort inset checks require scroll movement only when
that viewport has actual scroll extent, and always retain the viewport,
navigation-clearance, detail-tap, and Skip-action checks.
