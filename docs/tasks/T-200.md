# T-200 — Unify transaction-detail confirmation

## Problem

The transaction detail screen can show both a review-banner `Confirm` action
and a lower `Confirm parsed details` action. The first changes only status;
the second records only eligible parse feedback. The low-trust banner can
remain after the first action, leaving the user with repeated and ambiguous
confirmation prompts.

## Scope

- Replace the duplicate confirmation controls with one visible `Confirm
  details` action in a unified review panel. Show the stored amount and
  currency, direction, payee, and category so the user can check them before
  confirming.
- Add one atomic repository operation for the UI action. For eligible review
  rows (`needs_review` or `asked`), set status to `confirmed`. For any row,
  record a parse verdict only when the existing retained-SMS/evidence guard
  succeeds. A row outside review status remains status-unchanged.
- Reuse the existing parse-verdict marker, confidence, context, and ledger
  refresh contract. Preserve the legacy `confirmParse` API/ID/tests; the
  unified command uses a unique per-action feedback ID for stale-undo safety.
- Return an undo receipt that restores only this action's prior status metadata
  and removes a parse event only when this action created it. An earlier parse
  confirmation must survive. Do not create a category-prediction feedback
  event.
- Reject deleted, non-transaction, or duplicate rows. Analytics exclusion or
  missing payment-source attribution alone does not disqualify a legitimate
  transaction.
- Guard repeated taps, expose loading/disabled state, show success, and give
  useful feedback for ineligible/no-op/error outcomes. Keep the existing
  correction action separate.

## Acceptance

- Regression-first detail UI test proves there is exactly one confirmation
  action and that it shows the stored amount, direction, payee, and category.
- Confirming a review row resolves its status and, only when existing evidence
  rules allow, creates exactly one parse verdict. No amount, direction, payee,
  category, or source field changes; no category feedback is written.
- An eligible parse-only confirmation on a non-review status preserves that
  status. Already-confirmed parse evidence is not duplicated.
- Undo restores the prior review status and removes only newly-created parse
  evidence. Undo leaves a preexisting parse confirmation intact.
- Deleted, non-transaction, duplicate, missing-SMS, and missing-evidence cases
  cannot gain parse confirmability; status confirmation cannot bypass the
  excluded-row guard. Analytics/payment-source exclusions alone remain
  compatible with confirmation.
- Verify compact 320dp / 2x text, busy/loading and rapid taps, failure/no-op
  feedback, and visible confirmed state without repeated prompts.
- Focused and full Flutter tests, touched-directory `America/New_York` tests,
  analyzer, formatter, documentation links, `git diff --check`, and complete
  GitNexus change analysis pass.
