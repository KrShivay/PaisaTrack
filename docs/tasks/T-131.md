# T-131 — Numeric trust boundary

**Invariant:** every amount, direction, and timestamp in `transactions` must be
reproducible by re-running a deterministic normalizer over a byte range of stored
source text. Today `LlmExtractor` returns a full record and validates only
plausibility, never that the value appears in the message.

Do the three sub-tasks in order. T-131c must not land before T-131b, or there is
a build in which unverified model amounts can be written.

### T-131a — Add `FieldEvidence` to the record contract   [P0] [~M]
Files:    `lib/data/models/normalized_transaction_record.dart`,
          `lib/data/db/tables/transactions_table.dart`,
          `lib/data/repositories/transaction_repository.dart`
Depends:  none
Change:   Add `class FieldEvidence { String field; int start; int end; String
          verbatim; String extractor; }` and `List<FieldEvidence> evidence` on
          `NormalizedTransactionRecord`. Persist as `evidence_json` (nullable, so
          existing rows are valid). Serialize in `toJson` with stable wire names.
Tests:    Round-trip serialization; migration test proving existing rows read
          back with null evidence.
AC:       Schema is additive; no existing behaviour changes.
Impact:   `impact({target: "NormalizedTransactionRecord", direction: "upstream"})`
          — this is the frozen parser contract; expect wide blast radius.

### T-131b — Add `SpanVerifier` and emit evidence from deterministic parsers   [P0] [~M]
Files:    `lib/capture/span_verifier.dart` (new),
          `lib/capture/template_engine/field_normalizer.dart`,
          `lib/capture/generic_transaction_parser.dart`,
          `lib/data/repositories/transaction_repository.dart` (write guard)
Depends:  T-131a
Change:   `SpanVerifier.verify(body, evidence)` re-anchors each span and asserts
          `body.substring(start, end) == verbatim`, then re-parses the substring
          through `FieldNormalizer` and asserts the same value. Template and
          generic parsers already know their match offsets — emit evidence for
          `amount`, `direction`, and `ts`. Add a repository write guard: refuse
          a record whose three required fields lack verifying evidence — assert
          in debug, downgrade to `needs_review` in release.
Tests:    Every existing bank fixture still parses to the same record **and**
          produces verifying evidence. Tampered-span test refuses.
AC:       Template and generic paths behave identically, now with evidence.

### T-131c — Replace `LlmExtractor` with `LlmFieldLocator`   [P0] [~M]
Files:    `lib/capture/llm_extractor.dart` → `lib/capture/llm_field_locator.dart`,
          `lib/capture/parser_cascade.dart:44-47`
Depends:  T-131b
Change:   The model returns **quotations, not values**: `{amount_text,
          direction_text, date_text, merchant_text, account_text, message_kind}`.
          Each quoted string must occur verbatim in the body; resolve to offsets
          and hand the substring to `FieldNormalizer`. A hallucinated amount is
          not in the body and the record is refused → quarantine, never a
          transaction. Descriptive fields (merchant, description) may still be
          model-authored per the owner's decision; they are labels, not evidence.
          Remove `LlmExtractor` in the **same** change.
Tests:    Adversarial fixtures where a plausible-but-absent amount is the
          tempting answer — each must refuse. Verbatim-with-different-formatting
          ("1,250.00" vs "1250.00") must refuse rather than coerce.
AC:       No model-produced monetary value can reach `transactions`. The refusal
          rate is recorded (T-143c) — zero would mean verification is not running.
Rationale: `docs/sms-intelligence-design.md` §4.
