## Owner decisions (2026-10-10)

- Refunds typically arrive within **3-5 business days**; matching may look back
  **up to 31 calendar days** from the purchase.
- Attribution default: **purchase period** (owner, 2026-10-10), posting date
  stays visible; one switch keeps posting period available.
- Auto-link: **suggest only** (owner, 2026-10-10); T-100b1c is not built.

## Matching window (design)

- One constant `RefundMatchPolicy.lookbackDays = 31`, and
  `typicalBusinessDays = 5` (weekday-only count; no holiday table). Both live
  in the new policy class (T-100b1a), not scattered literals.
- Applies to **suggested/heuristic** candidates only: credit `ts` in
  `[purchase.ts, purchase.ts + 31d]`. Within 5 business days -> ranked "likely";
  day 6-31 -> shown as "possible", never auto-selected, needs review.
- Exact stored reference equality (ADR 0026) and a user-chosen original are not
  limited by the window (ADR 0026: preserve arbitrarily late dates). This
  reconciles ADR 0026 with the owner's 31-day rule; ADR 0026 text about "the
  correlator's unapproved 30-day heuristic" is superseded for heuristics by
  this decision (note the ADR 0026 line when approving).
- `EventCorrelator._matchWindow` is 30 days and shared by UTR, reversal and
  refund tiers (`lib/capture/event_correlator.dart:43`); add a separate
  `_refundWindow` rather than changing the shared one.
- Hard guards unchanged from the audit: settled eligible debit, settled
  positive credit, same SourceCurrency bucket, purchase not after credit,
  cumulative linked <= original, ambiguity abstains.

## Attribution switch (design for both)

`enum RefundAttribution { purchasePeriod, postingPeriod }`, persisted as one
local setting (`refund_attribution`, default per owner answer), read by one
function `NetSpend.attributionTs(link) -> int`:
purchasePeriod => original debit `ts`; postingPeriod => refund credit `ts`.
Net for any period/category = eligible gross debits in period - sum(linked
refund amounts whose `attributionTs` falls in the period). Because it is
computed at read time from links, flipping the switch needs **no data
migration and no backfill**; gross, per-link amounts and both dates stay in
source rows. `reverses` links always net in the original purchase period
(plan: credit-card-accounting). Reimbursements (`repays`) are excluded from
net by default (separate owner decision, not blocking).

Recommended default: **purchasePeriod**, with the posting date always visible
("refunded Oct 3") and a "by month received" toggle. Reasoning: with 3-5 day
typical lag, only boundary refunds change month, so restatement is rare and
small; category and budget totals then reflect what the purchase really cost;
posting-period would leave a month with a refund of a prior-month purchase
showing negative/odd category spend; and it matches the reversal rule and the
card plan. Cost: a closed month can change retroactively (mitigate: show
"restated by refund" badge and an explanation row, T-100c5). If the owner
prefers statement-like immutability, switch to postingPeriod by setting alone.

## Reuse (no new ledger)

- Candidate discovery/preview: `RefundLinkPreviewRepository` (read-only,
  consistent snapshot, reference-index lookup) - extend, do not fork.
- Storage: `transaction_links` with `link_type='refunds'`, `from`=credit,
  `to`=original debit, `created_by` system|user, `basis` text
  (`lib/data/db/tables/transaction_links_table.dart:6`). Partial refund = the
  credit's own amount (whole-credit allocation to one original; a credit split
  across several originals is out of scope for v1). No new column needed, so
  **no schema and no ADR 0037** unless T-100b2d (dismissal memory) is
  approved. `financial_events` stays dormant (audit item 8).
- Undo: ADR 0031 correction-receipt pattern (validate every affected row
  against its recorded post-state; conflict leaves everything intact). A link
  is durable by itself, so "undo after restart" = **Unlink** from detail with
  the same stale-state guards; the transient Undo snackbar uses the receipt.
  Shared contract owner: T-157b.
- Amount arithmetic: Money helper from [T-165c](T-165c.md) (cap and remaining
  checks exact). If T-165c1 has not landed, b1b must use the preview's decimal
  units helper (`refund_link_preview_repository.dart:593`), not `double`.

## Scope and non-goals

Deliver reversible full/partial refund, reimbursement, and reversal links;
define one net-spending result consumed by aggregate callers. Preserve each
original debit/credit row. No automatic edits to source rows, card bill
accounting (owned by T-190), currency conversion, or schema until ADR approval.
