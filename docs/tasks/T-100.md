# T-100 — Refund, reimbursement, and reversal accounting

Status: proposed; split before implementation. Existing behavior is linked in
[architecture](../architecture.md) and current source below.

## Current state and real gaps

- `EventCorrelator.correlateRefund` implements reference or unique
  counterparty/amount matching and distinguishes full/partial confidence
  ([helper](../../lib/capture/event_correlator.dart#L230)); a search of current
  `lib/` found no caller. **Unverified:** production refund wiring. The opened
  ingestion path writes a duplicate `echo` link after transaction insertion,
  not a refund link ([source](../../lib/capture/sms_ingestion.dart#L484)).
- `TransactionLinks` supports `refunds`, `reverses`, `settles`, and transfer
  link types ([table](../../lib/data/db/tables/transaction_links_table.dart#L6));
  link storage does not itself define net totals or user-reviewed amounts.
- `FinancialEligibility` centralizes settled debit inclusion, but its current
  predicate does not apply refund edges ([source](../../lib/data/analytics/financial_eligibility.dart#L9)).
- `FinancialEvents.netAmountPaise` exists, but no current repository consumer
  was found; audit its schema/migrations before reuse
  ([table](../../lib/data/db/tables/financial_events_table.dart#L4)).
- Gap: multi-refund aggregation, over-refund protection, user link/review/undo,
  immutable source amounts, explained totals, backup compatibility and one
  shared net-spending contract. Existing links do not prove those outcomes.

## Scope and non-goals

Deliver reversible full/partial refund, reimbursement, and reversal links;
define one net-spending result consumed by aggregate callers. Preserve each
original debit/credit row. No automatic edits to source rows, card bill
accounting (owned by T-190), currency conversion, or schema until ADR approval.

## Slices

### T-100a — Audit and accounting contract (~M)

- **Goal:** inventory `EventCorrelator`, ingestion, `transaction_links`,
  `financial_events`, `FinancialEligibility`, aggregate consumers, archive
  paths, and `PV-04`; define gross/net, partial/many-link, reimbursement,
  reversal, currency, unlinked credit, and double-count rules.
- **Acceptance evidence:** source map; scenario table with round synthetic
  amounts; old/new aggregate parity expectations; proposed schema diff and ADR
  requirement; no implementation claims. Characterize with
  `test/capture/event_correlator_test.dart`,
  `test/data/financial_eligibility_parity_test.dart`, and
  `test/features/backup/encrypted_backup_service_test.dart`.
- **Depends:** none; see the scope note below for the completed presentation
  work relevant to this audit.
- **Schema/ADR:** none for audit; ADR before any relationship or aggregate
  schema change. Prefer current links/events after proving they cover semantics.
- **Privacy:** synthetic XBANK transactions only; never use real SMS or
  statements.
- **Rollback:** remove proposal only.
- **Test strategy:** define synthetic cases for one full refund, two partial
  refunds, over-refund, ambiguous candidates, reversal, repeated import,
  foreign currency, and unlinked credit.
- **Exact command:** `flutter test --no-pub test/capture/event_correlator_test.dart test/data/financial_eligibility_parity_test.dart test/features/backup/encrypted_backup_service_test.dart`.
- **Readiness:** owner accepts accounting rules; every caller of spend totals is
  inventoried; migrations, backup/delete, undo and currency treatment are
  decided.

### T-100b1 — Persist guarded refund relationships (~M)

- **Goal:** implement approved relationship persistence and guards by reusing
  existing correlator/link code; expose no user mutation path yet.
- **Acceptance evidence:** correlator/repository tests prove source rows and
  amounts stay unchanged, duplicate ingestion is idempotent, cumulative links
  stay within approved limits, and ambiguous candidates stay unlinked. Add a
  migration test only if the audit requires schema changes.
- **Depends:** T-100a and accepted ADR.
- **Schema/ADR:** additive migration only if audit proves necessary; update both
  archive encodings, foreign-key checks, delete/reset and migration tests.
- **Privacy:** synthetic masked counterparties and round amounts.
- **Rollback:** retain additive relationship rows on app rollback.
- **Test strategy:** full/partial/many links, currency mismatch, conflicting
  link attempt, and archive round-trip if schema changes.
- **Exact command:** `flutter test --no-pub test/capture/event_correlator_test.dart test/data/repositories/transaction_link_repository_test.dart test/data/db/app_database_transaction_link_migration_test.dart test/features/backup/encrypted_backup_service_test.dart` (the repository and migration files are added if the audit requires them).
- **Readiness:** ADR accepted; relationship constraints and archive behavior
  reviewed.

### T-100b2 — Preview, review, and durable undo (~M, re-estimate at grooming)

If durable undo needs new schema, split it into T-100b2a (undo storage +
migration + archive coverage) and T-100b2b (preview/review UI) before Ready.

- **Goal:** let a user create or remove a relationship only after preview and
  confirmation, with durable Undo.
- **Acceptance evidence:** synthetic repository/widget tests cover preview
  totals, stale-preview rejection, review, undo after restart, conflicting links
  and unchanged source facts.
- **Depends:** T-100b1, T-157b shared correction/undo contract, and PV-04
  explanation contract.
- **Schema/ADR:** reuse the approved relationship state; any added undo state
  requires additive migration, backup, delete/reset and migration coverage.
- **Privacy:** synthetic masked counterparties and round amounts.
- **Rollback:** hide the review entry point; preserve decisions and expose Undo.
- **Test strategy:** synthetic before/after pairs and restart between action and
  Undo.
- **Exact command:** `flutter test --no-pub test/data/repositories/transaction_link_review_test.dart test/features/transactions/refund_link_review_test.dart test/features/backup/encrypted_backup_service_test.dart`.
- **Readiness:** preview ownership, stale-state handling and Undo lifecycle are
  reviewed.

### T-100c — Canonical net totals (~M)

- **Goal:** make aggregates compute net-spend once from eligible debits and
  approved links; explain linked/unlinked credits and exclusions consistently.
- **Acceptance evidence:** parity tests across dashboard, trends, Ask/insights,
  and future budgets; exact fixture totals for full and partial refunds; source
  currency buckets remain separate; `FinancialEligibility` remains the common
  base.
- **Depends:** T-100b2, T-165c conversion decision if paise representation is
  touched, and T-164c/d/PV-04 explanations.
- **Schema/ADR:** no new schema unless proven by audit; any field or aggregate
  contract change requires ADR and additive migration.
- **Privacy:** synthetic data only; no exported row-level metrics.
- **Rollback:** preserve original gross transactions and links; revert aggregate
  consumers to the prior computed rule, retaining additive state.
- **Test strategy:** canonical fixture oracle plus cross-caller parity and
  exclusion matrix.
- **Exact command:** `flutter test --no-pub test/data/financial_eligibility_parity_test.dart test/data/repositories/dashboard_repository_test.dart test/intelligence/assistant/query_engine_test.dart test/intelligence/derived_reads_service_test.dart`.
- **Readiness:** T-100a/b reviewed; every financial aggregate caller migrated
  or explicitly deferred; unresolved-credit policy accepted.
