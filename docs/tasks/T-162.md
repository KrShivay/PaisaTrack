### T-162b — Sender-onboarding evidence and allowlist review gate  [P1]

Goal: no header token is added to `SmsFilter.bankTokens` or to a template
`sender_patterns` list without reviewable, synthetic, privacy-clean evidence.

Evidence record (one JSON file per sender in `test/fixtures/sender_evidence/`,
schema documented in `docs/sender-onboarding.md`):

```
{ "schema": 1,
  "header": "XX-EXAMPLE",            // DLT header shape, no phone numbers
  "token": "EXAMPLE",                // value that would enter bankTokens
  "institution": "Example Bank",
  "kind": "bank|card|wallet|broker|payroll",
  "template_fingerprint": "sha256:<hex>",   // see below
  "cases": [ { "id": "...", "body": "<synthetic>", "direction": "credit",
               "expected": { "amount": 1234.5, "direction": "credit",
                 "channel": "netbanking", "account_tail": "1234",
                 "template_id": "example_credit_v1|null" } } ],
  "negative_cases": [ { "id": "...", "body": "<otp or promo>", "allowed": false } ],
  "provenance": "public-doc|owner-redacted|synthetic",
  "reviewer": "", "reviewed_on": "" }
```

Template fingerprint: sha256 of the body with digits → `#`, amounts →
`<AMT>`, dates → `<DATE>`, account tails → `<ACC>`, names/VPAs → `<NAME>`,
whitespace collapsed, lowercased. It groups messages by shape without storing
content. Rules: bodies are synthetic or fully redacted (fixtures may not
contain real names, numbers, VPAs, balances, OTPs); at least 2 positive cases
(debit and credit where the sender supports both) and 2 negative cases (OTP,
promo); expected values are asserted through the shipped `ParserCascade`.

### T-162d — Employer/payroll alias recognition after parser evidence  [P2]

Goal: recognise "this credit is salary from employer X" deterministically,
only after the parser has verified the facts, and never from a name alone.

Preconditions (all required; otherwise abstain): record is a verified credit
(`SpanVerifier` evidence present, `lifecycle_state = settled`); account/channel
context exists (non-null `accountHint`, channel `netbanking` or `unknown` for
NEFT/IMPS/ACH, never `upi` person VPAs and never `card`); cue `salary_word`
or `payroll_word` (from T-205b) or an existing user payroll alias; amount
band is not used as evidence. Alias storage: a `rules` row with
`match_type = 'merchant'` and `set_category_id = 'income_salary'`, created
only by explicit user confirmation ("Is this your salary?") or by T-205 payee
review; no auto-learning. A repeated credit pattern (≥3 months, same alias,
credit, similar day) may *suggest* the question, never apply it.
