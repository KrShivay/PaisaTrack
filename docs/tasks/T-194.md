# T-194 — Trial compressed ARM64 native-library packaging

## Goal

Measure whether AGP's legacy JNI packaging can reduce the signed ARM64 APK
below 27,000,000 bytes without changing app behavior. This is a bounded
packaging experiment, not permission to publish a new release.

## Baseline and scope

- Baseline: signed ARM64 `0.1.3+2011`, package `com.paisatrack`, effective
  version code `4011`; APK size 56,750,764 bytes. The six uncompressed `.so`
  entries total 53,639,672 bytes.
- Trial: set `variant.packaging.jniLibs.useLegacyPackaging = true` for the
  release variant through AGP's Variant API. Keep Dart/native app sources,
  dependencies, manifest inputs, and version unchanged. The debug variant must
  retain the default uncompressed packaging behavior.
- Build a signed candidate with the existing production signing identity.
  Never stage, print, copy into tracked files, or commit the keystore or its
  properties. Do not read phone/user data.
- Android's `useLegacyPackaging` setting compresses native `.so` files in the
  APK. Record the resulting manifest extraction flag and verify archive
  integrity/alignment. See the [AGP JNI packaging reference](https://developer.android.com/reference/tools/gradle-api/8.3/com/android/build/api/dsl/JniLibsPackaging)
  and [Android app-size guidance](https://developer.android.com/topic/performance/reduce-apk-size).

## Acceptance

1. Candidate signed ARM64 APK is at most 27,000,000 bytes.
2. Package, version name, effective code, and production certificate match the
   baseline exactly.
3. All six ARM64 `.so` paths and uncompressed contents match hashes from a
   same-source, same-toolchain build with the default packaging setting; no
   library is missing or added. Compare against the published APK and record
   any pre-existing build variance separately.
4. ZIP test and `zipalign -c -v 4` pass. Record APK SHA-256, per-entry sizes,
   compression methods, and manifest `extractNativeLibs` value.
5. A debug ARM64 build passes with `extractNativeLibs=false` and uncompressed
   `.so` entries, confirming the setting is release-variant only.
6. Document the expected increase in installed native-library storage and
   possible install/startup cost from extraction. Measure installed size and
   cold-start behavior on the supported physical ARM64 phone before adoption.
7. Keep this task open until the physical storage and startup checks pass;
   revert the packaging flag if they fail. The published download remains
   unchanged by this trial.

## Dependencies and privacy

- No code or schema dependency. Use the signed baseline in `docs/release-signing.md`.
- The supported phone was online for the separate published-release install on
  2026-09-30, but no T-194 candidate was installed or measured. No emulator,
  release publication, or private phone data is part of this trial.

## Rollback

Remove the single `useLegacyPackaging` setting. The current published APK and
signing material remain untouched.

## Results

The signed ARM64 candidate was built from `82907bf` with Flutter 3.44.4 and
AGP's existing release configuration. It is 26,180,416 bytes, SHA-256
`cb9a3deb34207ea4b9aef251f7ce411166e7ac59cc4d5cff3690844691672e29`;
the published baseline is 56,750,764 bytes, SHA-256
`218308d98cd8b0105adfe74d5e49cae5183ddb964f889e419ed5199888be50c4`. The
candidate saves 30,570,348 bytes (53.9%) and meets the APK-size target.

Both APKs report package `com.paisatrack`, version `0.1.3`, effective code
`4011`, and production certificate SHA-256
`6a00ef7a3557533e091011d6166c0c45a3bc7a1e540dd2eed4640c88c1ed9163`. ZIP
integrity, APK signature verification, and `zipalign -c 4` pass. The candidate
contains the same six ARM64 library paths and 53,639,672 uncompressed library
bytes. `useLegacyPackaging=true` compresses all six entries and the merged
manifest reports `extractNativeLibs=true` (the published baseline reports
`false`). A same-source, same-toolchain signed control build with the setting
omitted has identical content hashes for all six libraries, confirming that
the trial changed compression only. Two library hashes (`libapp.so` and
`libdartjni.so`) differ from the older published artifact in both control and
candidate; the four other library hashes match. Do not claim identity to the
published native binaries beyond paths and uncompressed total size.

| ARM64 library | Uncompressed bytes | Trial compressed bytes / method | Control bytes / method |
|---|---:|---:|---:|
| `libapp.so` | 8,389,520 | 3,359,244 / Deflate | 8,389,520 / Stored |
| `libdartjni.so` | 124,776 | 23,717 / Deflate | 124,776 / Stored |
| `libflutter.so` | 11,580,816 | 5,408,682 / Deflate | 11,580,816 / Stored |
| `liblitertlm_jni.so` | 20,790,648 | 9,038,123 / Deflate | 20,790,648 / Stored |
| `libmediapipe_tasks_text_jni.so` | 7,566,368 | 2,990,225 / Deflate | 7,566,368 / Stored |
| `libsqlcipher.so` | 5,187,544 | 2,285,379 / Deflate | 5,187,544 / Stored |

At install time, extraction is expected to add the six uncompressed libraries
beside the compressed APK. From archive sizes, that projects about 23,069,324
additional bytes on-device versus the uncompressed baseline; this is not a
physical measurement. Android documents that `extractNativeLibs=false` loads
libraries directly from the APK, which can improve loading speed and reduce
installed size. The supported phone was online for the separate published-
release launch, but the compressed candidate remains uninstalled; storage and
cold-start behavior are unmeasured. No experimental APK was installed or
published; T-194 remains open for device acceptance.
