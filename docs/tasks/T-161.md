### T-161a — Return privacy-safe SMS scan outcome counts  [P0] [~M]
Files:    `android/app/src/main/kotlin/com/paisatrack/capture/SmsInboxReader.kt`,
          `android/app/src/main/kotlin/com/paisatrack/capture/SmsFilter.kt`,
          `android/app/src/main/kotlin/com/paisatrack/MainActivity.kt`,
          `lib/capture/sms_backfill.dart`,
          `lib/capture/sms_ingestion.dart`,
          `lib/features/sms/sms_lookup_sheet.dart`,
          related capture/Android tests
Depends:  none; T-161b adds durable failure reasons after this contract
Change:   Return aggregate counts for each bounded inbox page and carry them
          through the import result/progress: scanned, filter-rejected,
          unknown-sender, accepted, parsed, unparsed, created, and already
          known. Count only; never include message bodies, sender values,
          identifiers, or raw error payloads in progress or logs.
Tests:    Kotlin tests for accepted/rejected/unknown admission counts and
          missing-field classification; Dart tests for payload decoding, page
          aggregation, parse/created/already-known counts, and privacy-safe
          error handling.
AC:       A completed SMS scan reports every requested count consistently across
          pages, while raw message content and personal identifiers remain
          confined to the existing on-device ingestion/database boundary.
Rationale: `TASKS.md` T-161a — users currently see only coarse “checked/found”
           totals and cannot tell whether a message was rejected, unreadable,
           parsed, created, or already present.

### T-161b — Persist privacy-safe failure reasons and version-gated retry [P0] [~M]
Files:    `lib/data/db/tables/raw_sms_table.dart`, `lib/data/db/database.dart`,
          `lib/capture/parser_version.dart`, `lib/capture/sms_ingestion.dart`,
          `lib/capture/sms_backfill.dart`, backup serialization, and migration /
          capture tests
Depends:  T-161a; T-161c owns the user-facing unreadable-message surface
Change:   Add nullable `parser_version` and allowlisted `failure_reason` fields
          to retained raw SMS rows. Stamp every parse attempt with the current
          parser contract version; use `unparsed` or `processing_error` only,
          never exception text, body, sender, identifiers, or stack traces.
          Skip same-version failed rows and retry retained failures only when
          the parser version increases.
Tests:    v13→v14 migration, parse miss/error persistence, same-version skip,
          upgraded-version retry, backup compatibility, and retention/privacy.
AC:       Failure metadata survives process errors and upgrades without raw
          content leakage; repeated scans do not retry the same failed row at
          the same parser version; a parser upgrade makes retained failures
          eligible exactly once.
Rationale: `TASKS.md` T-161b — failed/unparsed rows currently have no durable,
           retryable explanation and are re-attempted without a parser-version
           contract.

### T-161d — Refresh SMS permission on app resume  [P1] [~S]
Files:    `lib/capture/permissions/sms_permission_lifecycle.dart`,
          `lib/app.dart`, `lib/features/sms/sms_permission_status_card.dart`,
          `lib/features/settings/settings_screen.dart`,
          `lib/features/transactions/transactions_screen.dart`, and
          permission/lifecycle widget tests
Depends:  T-161a; T-161b; existing `SmsPermissionController.recheckStatus`
Change:   Observe the app lifecycle at the root and re-read the Android SMS
          permission whenever the app resumes. Share one status card between
          Settings and Activity so granted, denied, permanently denied, and
          unavailable states use the same recovery actions and wording.
Tests:    Provider recheck, granted/denied/permanently-denied card behavior,
          and app-resume refresh tests; preserve Settings and Activity coverage.
AC:       Returning from Android settings updates both user-facing status
          surfaces without a cold start; denied states expose runtime request
          or app-settings recovery as appropriate; no capture/query semantics
          change.
Rationale: Permission can be changed outside the app while it is backgrounded;
           cached status otherwise leaves the root shell and capture surfaces
           stale until a cold start.
