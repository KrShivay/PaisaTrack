# T-157 — Riverpod boundary hardening

Two screens write to the database directly from widget event handlers instead
of through a repository, and the transaction-correction "optimistic update +
undo" pattern is hand-duplicated four times across two files. This narrows
T-130's "split reads/commands/corrections" gap for the specific files the
audit found — it does not replace T-130's broader data-layer scope.

### T-157a — Move raw Drift writes out of recurring_screen.dart and insights_screen.dart   [P2] [~M]
Files:    `lib/features/recurring/recurring_screen.dart:294-302,313-321`,
          `lib/features/insights/insights_screen.dart:197-200`,
          `lib/data/repositories/`
Depends:  none
Change:   Add `RecurringRepository.setStatus(seriesId, status)` and
          `InsightsRepository.dismiss(id)` — first run `impact()` on the
          existing repository classes to confirm neither method already exists
          under a different name — and replace the two
          `db.update(...)...write(...)` blocks in the screens with calls to
          them. No change to the write's SQL/effect, only to where it's called
          from.
Tests:    Repository-level test for each new method against an in-memory DB;
          existing recurring/insights widget tests pass unchanged.
AC:       Neither screen file calls `db.update(` directly; both go through
          their repository.
Rationale: every other mutation in the app already goes through a repository —
          these two are the exceptions the audit found.

### T-157b — Extract the shared category-correction + undo controller   [P2] [~L — split into T-157b1/T-157b2 if estimate exceeds a day]
Files:    `lib/features/transactions/transaction_detail_screen.dart:117-220`
          (`_changeCategory`, `_selectCategoryDirectly`),
          `lib/features/review/weekly_review_screen.dart:245-352`
          (`_confirmItem`, `_recategorizeItem`),
          new `lib/features/transactions/transaction_correction_controller.dart`
Depends:  none, but land before T-158b so the screen split consumes the
          finished controller rather than re-deriving it. **Must be preceded by
          T-159a's characterization tests — this is the highest-risk extraction
          in the plan.**
Change:   Extract the "resolve db → resolve repository → optimistic setState →
          `repo.correctCategory` → push undo token" sequence — duplicated four
          times across two files, twice within `transaction_detail_screen.dart`
          alone — into one `TransactionCorrectionController`. Each of the four
          call sites becomes a thin call into it. No change to what
          `correctCategory` is called with or when undo is pushed.
Tests:    T-159a's characterization tests must exist and pass against the
          *current* four call sites before this starts; re-point them at the
          controller after and confirm they still pass.
AC:       `_changeCategory`, `_selectCategoryDirectly`, `_confirmItem`, and
          `_recategorizeItem` each call the shared controller; undo behavior
          (toast, revert on tap) is unchanged.
Rationale: same repository call, same undo-token shape, hand-duplicated four
          times — the single biggest de-duplication in this plan, and the
          riskiest given today's near-zero coverage of the undo path.
