# T-208 — Performance plan and measurement harness (P1)

Status: Proposed brief, planning only — 2026-10-10. Budget table and design:
[performance plan](../plans/performance.md) (budget IDs `B-S*`, `B-Q*`, `B-R*`,
`B-I*`, `B-M*` are defined there; all values are *proposed, to calibrate*).

Owner request: "app needs to be faster". This task builds the host-measurable
proxies and the device-measurement kit; it does not duplicate:

- **T-115** (device profiling: cold start, 10k import, PSS) consumes the
  scripts from T-208l and the budgets here.
- **T-164b** (SQL filtering for Activity) must keep T-208b's query-plan tests
  green; T-208d adds its filter+search latency case when it lands.
- **T-165a** (10k/50k Activity profiling on release hardware) consumes
  T-208a's synthetic ledger and T-208j2's frame harness.
- **T-203** consumes T-208e's import benchmark for its before/after record.

## Evidence found

- DB already opens in a background isolate (`NativeDatabase.createInBackground`,
  `lib/core/crypto/database_cipher.dart:131`); no `journal_mode` pragma is set
  anywhere in `lib/` (grep), so SQLCipher runs in its default rollback-journal
  mode.
- Startup: `main()` calls `runApp` immediately
  (`lib/main.dart:12-18`) and defers WorkManager to a post-frame callback
  (`:20-23`). `PaisaTrackApp.build` watches five bootstrap providers before
  routing (`lib/app.dart:55-60`) and shows `_StartupScreen` until DB,
  permission and settings are ready (`:73-79`). `appDatabaseProvider`
  (`database_provider.dart:193-230`) resolves the keystore passphrase, opens,
  then runs `seedDefaultCategories` (parses the 87-category JSON and
  `insertOrIgnore`) and `seedDefaultFeatureFlags` on every launch
  (`:215-216`). `beforeOpen` runs `CREATE INDEX IF NOT EXISTS` x2 and
  `_ensurePaymentSourceTrigger` on every launch (`database.dart:274-295`).
- `DerivedReadsService` starts `_reconcileAtStartup` in its constructor
  (`derived_reads_service.dart:46-47`) and reads `MAX(updated_at)` and
  `COUNT(*)` over `transactions` (`readTransactionFreshnessSnapshot`,
  `:337-350`); `updated_at` has no index (`transactions_table.dart:12-34`), so
  this is a full scan at launch and twice per rebuild (`_startRun`,
  `writeFreshnessStamp`).
- Activity first page = 3 LEFT JOINs + `ORDER BY ts DESC, id DESC LIMIT 101`
  with `is_deleted/is_not_transaction/duplicate_of_txn_id` predicates
  (`transaction_repository.dart:257-326`); only `idx_transactions_ts(ts)`
  exists, so the `id` tiebreak needs a partial sort and the three flag
  predicates are evaluated per row. Filters/search are client-side
  (`transactions_screen.dart:66-110`) until T-164b.
- Day sections are `Column`s of all rows for that day
  (`transactions_screen.dart:847-870`), so virtualisation is per day, not per
  row.
- Dashboard load = 6 concurrent `customSelect`s
  (`dashboard_repository.dart:113-124`).
- Import: parsing/categorising runs on the UI isolate (`SmsIngestor` holds the
  main-isolate `AppDatabase`); only SQL executes in the DB isolate. Pages are
  200 messages (`constants.dart:67`) with one yield per page
  (`sms_backfill.dart:333`). `smsHistoryImportRunnerProvider` loads *all*
  transaction rows to build `knownTransactionIds`
  (`sms_backfill.dart:573`) — id-only select is enough.
- Existing perf-ish tests: `recurring_detector_test.dart:593` (scaling),
  `owned_transfer_reconciliation_test.dart:895` (Stopwatch). No shared
  synthetic ledger, no EXPLAIN assertions, no frame-timing test.
