# T-098 — Per-category monthly budgets

Status: proposed; the existing global prototype is not this feature.

## Current state and real gaps

- `BudgetRepository` stores one global monthly amount and merchant caps as
  `baselines` rows keyed by `monthly_budget` or `cap_*`
  ([source](../../lib/data/repositories/budget_repository.dart#L7)); it does
  not model category/month budgets.
- `FinancialEligibility.spendingDebit` is the shared settled, non-excluded,
  non-transfer debit predicate ([source](../../lib/data/analytics/financial_eligibility.dart#L26)).
- `FinancialEvents.netAmountPaise` exists, but current consumers and refund
  semantics were not established. T-100 must define net spend before budgets
  consume it.
- Gap: category/month limits, currency handling, period calendar, explanation
  of exclusions, threshold/remaining/projection, migration away from prototype,
  and budget archive/reset coverage.

## Scope and non-goals

Create optional per-category/per-month budgets with clear remaining and
threshold status based on canonical net spending. No automatic rollover,
cross-currency conversion, mandatory category creation, or use of forecast
estimates as settled actuals.

## Slices

### T-098a — Budget contract and prototype migration plan (~S)

- **Goal:** define amount currency, month calendar, category subtree behavior,
  refunds/reimbursements, exclusions, limit editing, threshold alerts and
  migration/retirement of global baseline keys.
- **Acceptance evidence:** scenario table and synthetic totals; map all current
  readers/writers of `BudgetRepository`, `baselines`, `FinancialEligibility`,
  and aggregate consumers. Characterize with
  `test/data/financial_eligibility_parity_test.dart`; add
  `test/data/repositories/budget_repository_test.dart` if no focused budget
  tests exist when implementation starts.
- **Depends:** T-100a/c and accepted budget decisions. See the [T-100 scope
  note](T-100.md#dependencies-and-readiness).
- **Schema/ADR:** no schema in contract slice; ADR before new budget table or
  migration.
- **Privacy:** local financial totals; synthetic category fixtures only.
- **Rollback:** proposal only.
- **Test strategy:** month-boundary, parent/child categories, uncategorized,
  excluded, linked/unlinked refunds, unknown currency and null budget.
- **Exact proposed command:**
  `flutter test --no-pub test/data/financial_eligibility_parity_test.dart test/data/repositories/budget_repository_test.dart`.
- **Readiness:** net calculation, financial calendar, category inheritance,
  currency, migration, backup/reset, and old prototype behavior accepted.

### T-098b — Dedicated category/month model (~M)

- **Goal:** store one user limit per category, calendar month and source
  currency, preserving the old baseline prototype until migration/retirement is
  proven safe.
- **Acceptance evidence:** additive migration and rollback tests; CRUD,
  uniqueness, backup/restore, reset/delete, duplicate month and currency tests.
- **Depends:** T-098a, T-100 canonical net contract, accepted ADR.
- **Schema/ADR:** dedicated table preferred; additive migration only; generated
  Drift code and migration tests in implementation task.
- **Privacy:** encrypted local database; no new external processing.
- **Rollback:** dual-read or compatible fallback through one release window;
  never delete legacy keys until verified copy and recovery behavior.
- **Test strategy:** synthetic budgets for two categories/months/currencies and
  old global value.
- **Exact proposed commands:** `flutter test test/data/repositories/category_budget_repository_test.dart test/data/db/app_database_budget_migration_test.dart test/features/backup/category_budget_backup_test.dart`,
  then `flutter analyze --no-pub` and full `flutter test` per
  [COLLABORATION.md](../../COLLABORATION.md).
- **Readiness:** migration preserves existing global setting or owner approves
  retirement; archive formats and deletion are covered.

### T-098c — Remaining, thresholds and projection UI (~M)

- **Goal:** show actual net spend, remaining, threshold and optional forecast
  with clear separation between actual and projected values.
- **Acceptance evidence:** `flutter test test/data/category_budget_net_parity_test.dart test/features/budgets/category_budget_screen_test.dart`
  (repository parity with shared eligibility/net fixtures; widgets across
  empty/error/partial periods, large amounts, accessible large text and
  category hierarchy); physical device evidence if release flow requires it.
- **Depends:** T-098b, T-100c, PV-04 visibility explanations and T-167/PV-07.
- **Schema/ADR:** derived projections should remain computed unless a measured
  need justifies durable state and a new ADR.
- **Privacy:** aggregate-only display; lock-screen/widget disclosure follows
  T-090/T-091 decisions.
- **Rollback:** hide new screen/alerts; preserve budget values.
- **Test strategy:** synthetic amounts around every threshold and month edge;
  excluded/pending/refund/transfer cases must match canonical fixture totals.
- **Readiness:** every number is sourced from shared eligibility/net code;
  projection is labeled; user can change/delete a limit.

## Files likely touched

`lib/data/repositories/budget_repository.dart`, new budget table and generated
Drift file, database migration, financial aggregate providers, budget UI,
encrypted backup service and focused tests.

## Dependencies and readiness

`FinancialEligibility` already centralizes base eligibility; the missing
prerequisite is the refund-aware contract owned by T-100. Do not promote T-098b
before T-100c is accepted. See the [T-100 scope note](T-100.md#dependencies-and-readiness).
