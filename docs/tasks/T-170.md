# T-170 — Release reliability and QA matrices (T-170d brief)

Status: proposed, planning only — 2026-10-10. This brief covers **T-170d**
only. T-170a (fault injection), T-170b (ADR 0021 device retention proof) and
T-170c (release smoke) stay on the board in [TASKS.md](../../TASKS.md); T-170d
reuses T-170b's device procedure and must not replace it.

Goal of T-170d: a repeatable, synthetic-only way to answer three questions.
(1) For every supported bank sender and template, which scenarios
(debit / credit / failed / reversal / OTP / promo / false-positive) are
proven, and which are known gaps? (2) When the app meets a sender it does not
support, what can the owner see, without any message content leaving the
phone? (3) Can a non-financial message from an allow-listed sender leak into
storage, UI or backup beyond the ADR 0021 retention rule?

No real SMS is read, pasted, committed or injected anywhere in this task.
Public-provenance fixtures and hand-written synthetic bodies (fake senders such
as `XX-HDFCBK`, masked `XX1234` accounts, round amounts) are the only inputs.

### Verified findings that shape the subtasks

1. **Registry and native allow-list disagree.** The registries accept sender
   patterns the native filter drops before Dart ever sees them. Header token
   is the segment matching `bankTokens`, else `parts[1]`
   (`SmsFilter.kt:135`); tokens not in the set (`SmsFilter.kt:20`) are
   counted as unknown-sender drops (`:80`).
   - `VM-KOTAKD-S` / `JD-KOTAKD-S`: Kotak registry matches
     (`kotak.json` line 2) and **real public fixtures use this sender**
     (`test/fixtures/sms/kotak/*short_upi*`), but `KOTAKD` is not in
     `bankTokens` (only `KOTAKB`). Native path would drop it.
   - Kotak RCS display names `Kotak`, `Kotak Mahindra Bank`, `Kotak811`
     (registry pattern 2) have no matching token.
   - `AD-HDFCBN` and `AX-ICICIP-S` are asserted as registry matches in
     `hdfc_icici_template_test.dart:31,148`; `HDFCBN` and `ICICIP` are absent
     from `bankTokens`.
   - Allow-listed tokens with **no template** (parse falls to the generic
     parser or `unparsed`): `ICICIT, SBIINB, SBICRD, CANBNK, BOIIND, YESBNK,
     IDFCFB, UNIONB, BOBSMS, RBLBNK, AUBANK, FEDBNK, IDBIBK, PHONPE, GPAYUP,
     AMZNUP, MOBKWK, SLICE, SLICEIT`. `SBIINB`/`SBICRD` are SBI senders but
     `sbi.json` only matches `SBIUPI`.
   Status: **verified by source reading**; no Kotlin test pins it yet (d2).
2. **Scenario coverage is uneven** (counts from `*.expected.json`, positives /
   negatives): axisbk 24/7, centbk 10/1, indusind 54/7, kotak 10/2, paytmb
   31/3, pnb 7/0, sbi 32/2, hdfcbk 2/0, icicib 2/0. No sender has a
   reversal-credit *positive* template; SBI reversal credits and IndusInd
   IMPS/P2A credits are pinned as negative "known gap" fixtures

3. `docs/sms-templates.md` says HDFC and ICICI "have sanitized fixture

## Matrix format (the artifact T-170d1 generates)

One row per **sender family x template id**; columns are the scenarios. Cell
values: `P#` = n passing positive fixtures, `N#` = n negative fixtures that
must yield `err: unparsed`/no transaction, `G` = known gap (documented, with
link), `-` = not applicable, `?` = unknown (fails `--check`).

| Sender family (header tokens; SmsFilter admits) | Template id | debit | credit | failed/declined | reversal | OTP | promo | false-positive |
|---|---|---|---|---|---|---|---|---|
| AXISBK (yes) | `axisbk_card_spent_v1` | P12 | - | N3 | G | ? | ? | N1 |
| ... | | | | | | | | |

Rules for filling cells:

- *debit/credit* come from `expected.ok.direction` of fixtures whose
  `parse_source` is `template`; `generic` fixtures are counted separately as
  `g#` and never satisfy a template cell.
- *failed/declined*, *reversal*, *OTP*, *promo*, *false-positive* come from
  negative fixtures; the generator infers the scenario from the file name
  keyword (`declined|failed`, `reversal`, `otp`, `promo|offer`,
  `kyc|bill_due|statement|mandate|reminder|cashback_future|money_request`),
  and any negative fixture with no keyword is reported as `?` so a human
  classifies it.
- Row for each *allow-listed token with no template* has the single status
  `unsupported (generic/unparsed)`; the generator lists it so telemetry work
  (d5/d6) has a denominator.
- A cell is only `P`/`N` if the existing fixture test actually asserts it
  (`sms_bank_fixture_coverage_test.dart`); `G` requires a link to the doc line
  that records the gap.

## Constraints and invariants

- ADR 0002/0011: no network, no telemetry upload. Any "telemetry" is local,
  in-memory or on-device and content-free.
- The filter is a privacy boundary: a message that never passes it is never
  stored. Do not widen it without a fixture-backed reason
  (`docs/sms-templates.md`: "add a bank token only with sanitized fixtures
  and exact parser assertions").
- Public fixtures stay capped at 0.85 confidence (ADR 0005).
- `device`-provenance fixtures are sanitized owner messages; they may be
  *counted* by the generator but must not be copied into new files or used as
  injection bodies. Injection corpus = hand-written synthetic bodies only.

## Data model and ADR needs

None for d1-d5, d7, d8. d6 (sender-token tally) is in-memory only; if the
owner wants it persisted across restarts it needs an ADR and the standard
schema/backup/delete coverage (next free ADR number: check
`docs/decisions/README.md`; 0036 is the highest at time of writing).

## Risks

- Adding bank tokens widens capture. Mitigate: parity test first (d2), token
  additions only with fixture evidence (d3), each addition has a negative
  fixture (OTP/promo) from that sender.
- A matrix that counts generic-parsed fixtures as "supported" overstates
  coverage; the generator separates `g#` from `P#`.
- Header-token tally (d6) can reveal which merchants/banks the owner deals
  with; keep it in-memory, dev-screen only, alphabetic tokens only, top 10.

## Rollout / flags

Docs, tests and a Python tool ship immediately. d3 changes native filtering:
land behind the existing release gates, rollback = revert the token list.
d6 is dev-screen only; no flag needed.
