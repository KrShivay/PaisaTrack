# T-210 — Test-suite speed (P2)

Status: Proposed brief, planning only — 2026-10-10. Design:
[performance plan](../plans/performance.md) section "Test-suite speed".
Hard rule for every subtask: **never weaken an assertion and never skip a
test**. Tags only select tests locally and balance shards; the required CI
run executes every test on every PR.

## Current state (evidence)

- 220 `*_test.dart` files: `test/features` 89, `test/data` 42, `test/capture`
  28, `test/core` 21, `test/intelligence` 19, `test/enrichment` 11,
  `test/fixtures` 4, `test/integration_test` 2, `test/assets` 1, `test/ci` 1,
  `test/security` 1, `test/widget_test.dart`.
- No `dart_test.yaml`, no `test/flutter_test_config.dart`, no `@Tags`,
  `@Timeout` or `skip:` anywhere under `test/` (grep).
- CI runs a bare `flutter test` after analyze and build_runner
  (`.github/workflows/ci.yml:55`, one job, no shards, no timing output, no
  artifacts). The default concurrency is the runner core count.
- `docs/development.md:43` tells developers to run `flutter test --no-pub
  --concurrency=1`, which makes a local full run strictly sequential (stale or
  at least inconsistent with the 4-core ~15 min figure; the T-210h task
  replaces it with measured guidance).
- 99 test files open `NativeDatabase.memory()`; 31 of them are widget tests;
  only 8 of those 31 use the Drift teardown helpers
  (`test/support/drift_widget_teardown.dart`: `unmountAndCloseDatabase`,
  `pumpDriftFrames`). Drift schedules a `Timer.run` when the last stream
  watcher cancels, so unclosed DBs risk "Timer still pending" failures or
  leaked watchers.
- 177 `pumpAndSettle` calls in 34 files (top: `weekly_review_screen_test` 18,
  `sort_safety_test` 15, `transaction_detail_correction_behavior_test` 14,
  `manual_entry_screen_test` 12). `BloomSkeleton` repeats forever unless
  reduced motion is on (`lib/core/widgets/bloom/bloom_skeleton.dart:46-52`);
  a visible skeleton or `CircularProgressIndicator` makes `pumpAndSettle`
  loop until its 10-minute fake-time timeout (about 6,000 frames of CPU), which
  looks like a hang and then fails.
- 14 files use `Future.delayed` or `Duration(seconds: ...)` (list from grep:
  `derived_reads_service_test`, `transaction_detail_screen_test`,
  `home_shell_back_navigation_test`, `raw_sms_repository_test`,
  `app_database_migration_test`, ...). Real waits outside `fakeAsync` cost
  wall time.
- 16 migration test files in `test/data/db/` (v2..v20 plus repair tests); the
  largest suites are `sms_ingestion_test` (2,414 lines),
  `encrypted_backup_service_test` (2,322), `transaction_repository_test`
  (1,937), `sms_backfill_test` (1,643).
- No golden tests exist (`matchesGoldenFile` has zero matches); a `golden` tag
  is therefore not needed now.
- Hypothesis (unproven; T-210a/b must confirm before building bundles):
  `flutter test` compiles each test entrypoint through one shared frontend
  compiler, so with 220 entrypoints the load phase is largely serialized and
  does not scale with `--concurrency`. The JSON reporter's hidden `loading
  <path>` pseudo-tests expose per-file load time separately from run time.

## T-210f — Duration-balanced shard planner   (~M ; suggested model: Sonnet)
- Depends: T-210a, T-210b   Parallel group: C
- Owns: `tool/ci/shard_tests.py` (new), `tool/ci/shard_tests_test.py` (new),
  `tool/ci/test_durations.json` (new, committed weights)
- Reads: T-210b artifact CSV; `flutter test --help` for
  `--total-shards`/`--shard-index`.
- Do:
  1. `shard_tests.py --shards K --index I [--weights tool/ci/test_durations.json]`
     prints the file list for shard I using longest-processing-time-first bin
     packing over `load_ms + run_ms`; unknown (new) files get the median
     weight; stable tie-break by path so shards are deterministic.
  2. `--check` verifies that the union of all shards equals the set of
     `test/**/*_test.dart` (no file lost or duplicated) — CI must run this
     before the matrix so a lost file fails loudly.
  3. `--update-weights events.json` rewrites the weights file.
  4. Fallback documented: native `flutter test --total-shards K --shard-index
     I` partitions without weights.
- Acceptance: unit tests for balance (max shard <= 1.15 x ideal on a skewed
  fixture), determinism, `--check` failing when a file is missing.
- Checks: `python3 -m unittest`.
- Privacy/rollback: tooling only.
- Consumer: **T-171a** wires K shards plus the Android/migration/fixture jobs
  into `.github/workflows/ci.yml` using this tool and uploads the JSON event
  files as failure artifacts.

## Target

Proposed, to calibrate after T-210b: full required CI run <= 6 min wall (K=4
shards, each <= 5 min), single-file loop < 15 s, zero tests that never finish,
and the 177 `pumpAndSettle` calls either bounded or proven to settle.
