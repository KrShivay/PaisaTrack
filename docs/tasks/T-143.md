# T-143 — Corpus, shadow mode, and metrics

T-143a–b and T-143c1 status: **COMPLETE** (2026-08-07). T-143c2–c3 remain open.

Phase A despite being tooling: without shadow mode and link fixtures, T-133–T-139
cannot be verified safely. No telemetry exists and none should — everything here
is CI or on-device.

### T-143a — Feature flags table   [P1] [~S]
Files:    `lib/data/db/tables/feature_flags_table.dart` (new),
          `lib/core/constants.dart`
Depends:  none
Change:   Move `AppConstants` behavioural thresholds into a `feature_flags` table
          seeded from the current constants, readable and writable from the dev
          screen. Constants become defaults, not the source of truth.
Tests:    Missing row falls back to the constant; edited row takes effect without
          restart.
AC:       Every threshold in the design's §10 table is toggleable without a
          rebuild.

### T-143b — Link and adversarial fixtures   [P1] [~M]
Files:    `test/fixtures/sms/` (new sequence shape),
          `test/support/fixture_loader.dart`
Depends:  none
Change:   Add two fixture shapes. **Sequences**: ordered multi-message cases with
          an expected event graph — auth→settle, debit→reversal, expense→refund,
          reminder→fulfilment, bank+wallet echo. This is the only honest way to
          test L5/L6. **Adversarial**: extraction bait where a plausible-but-
          absent amount is the tempting answer. ADR 0005 provenance rules apply
          unchanged — `public` or sanitized `device` only.
Tests:    The loader reads both shapes; existing single-message fixtures are
          unaffected.
AC:       T-131c, T-134b, and T-138c have fixtures to assert against.

### T-143c1 — Shadow table and isolated runner   [P1] [~M]

### T-143c2 — Deterministic shadow diff computation   [P1] [~M]
