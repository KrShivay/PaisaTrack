# T-130 — Residual data-boundary and coupling cleanup

Status: proposed, planning only — refreshed 2026-10-10 from a real import
graph. Supersedes the earlier "Unverified" cycle description; the cycle
members and seams below are source-verified.

## Method (reproducible)

Import graph of every `lib/**/*.dart` (210 files at 2026-10-10): each
`import`/`export` of a relative or `package:paisatrack/` path is an edge;
`part`/`part of` (Drift's `database.g.dart`) are not edges. Strongly connected
components of size > 1 are the cycles. The scratch script used for this
refresh is the seed for T-130a (Tarjan SCC, stdlib Python). Result:
**3 cycles, 9 files**; no other file participates in a cycle.

## Current state (evidence)

### Cycle 1 — database <-> duplicate rule <-> event correlator (3 files)

```
lib/data/db/database.dart
  -> lib/data/dedup/duplicate_match_rule.dart           (database.dart:8)
       -> lib/capture/event_correlator.dart             (duplicate_match_rule.dart:1)
       -> lib/data/db/database.dart                      (duplicate_match_rule.dart:2)
lib/capture/event_correlator.dart
  -> lib/data/db/database.dart                           (event_correlator.dart:2)
```

Why it exists:
- `DuplicateMatchRule.matches` takes a Drift row (`required Transaction
  existing`,
  [`duplicate_match_rule.dart:29`](../../lib/data/dedup/duplicate_match_rule.dart#L29))
  and reads `direction`, `lifecycleState`, `amount`, `ts`, `refId`,
  `counterpartyVpa`, `merchantRaw` from it. That is the
  `duplicate_match_rule -> database` edge.
- The rule calls two **pure static** helpers on `EventCorrelator`:
  `hasRefDisagreement` (`:46`) and `normalizeRefId` (`:55-56`). That is the
  `duplicate_match_rule -> event_correlator` edge, and `event_correlator`
  imports `database.dart` only for its own `Transaction` parameters
  (`event_correlator.dart:89,103,239`).
- `AppDatabase._backfillDuplicateLinks` (v1->v2 migration, ADR 0003) is the
  only use inside `database.dart`
  ([`database.dart:422-460`](../../lib/data/db/database.dart#L422)); the other
  caller is `DuplicateSuppressor`
  ([`duplicate_suppressor.dart:52-68`](../../lib/capture/duplicate_suppressor.dart#L52)).
  Tests call the rule directly in `test/capture/event_correlator_test.dart:60,97`
  and `test/capture/duplicate_suppressor_test.dart`; the backfill is exercised
  by `test/data/db/app_database_v2_migration_test.dart` and the v3/v8 migration
  tests.

## Constraints and invariants

- Pure refactors: no behaviour, schema, route or provider-name change. Keep
  public symbol names; where a symbol moves, keep a re-export or thin delegate
  so existing tests and callers compile unchanged until a later cleanup.
- No new dependency cycle (checker from T-130a is the gate).
- No monetary conversion, no algorithm change in duplicate matching: the
  rule's decisions must be byte-for-byte the same for the same inputs.
- ADR need: none. Stop and write one if a persisted contract or public API
  changes.

## Risks

- `DuplicateMatchRule` feeds a migration backfill (data-affecting) and the
  live suppressor; a subtle mapping error would mis-suppress transactions.
  Mitigate with the existing migration tests plus a new field-by-field parity
  test (see T-130b2).
- Provider moves can change Riverpod provider identity if a provider is
  re-declared instead of moved; moves must be cut/paste with the same
  top-level name.

## Rollout / flags

None; each subtask is an isolated revertable commit. Land the checker (a)
first with the current 3 cycles baselined, then ratchet down as b/c/d land.
