# T-130 — Residual data-boundary and coupling cleanup

Status: proposed; narrowed to avoid duplicate ownership with T-165b/c/d.

## Current state and real gaps

- [The board](../../TASKS.md) groups a database↔duplicate-rule import cycle, oversized
  repositories/screens, O(n²) owned-transfer reconciliation, and monetary
  `double`/SQLite REAL under T-130.
- `PaymentSourceRepository.reconcileOwnedTransfers` currently uses an SQL
  self-join for candidates, then greedily claims ordered candidate pairs with a
  `used` set; it does not prove a candidate is unique, so ambiguous pairs can
  be linked
  ([source](../../lib/data/repositories/payment_source_repository.dart#L109));
  T-165b owns optimizing and adversarially validating this query.
- Transactions store `amount` as SQLite REAL
  ([schema](../../lib/data/db/tables/transactions_table.dart#L36)); T-165c owns
  the integer-paise migration.
- T-165d owns splitting `TransactionRepository` reads/commands/corrections
  behind DTOs. T-130 must not repeat that extraction.
- Proposed residual scope is the import cycle and large screen/data modules
  outside T-165d, based on the board description. Exact cycle members and split
  seams are **Unverified** until source-mapped; do not guess from directory
  structure.

## Scope and non-goals

Reduce only confirmed dependency cycles and remaining oversized presentation or
data modules after T-165 ownership is removed. Preserve behavior and providers.
No monetary conversion, owned-transfer algorithm change, broad rewrite, API
renaming, or speculative abstraction.
